# GlobalPay — API Contract

**Document version:** 1.0  
**Status:** Proposed contract for implementation; not evidence that endpoints are already implemented  
**Product:** GlobalPay — AI-assisted international travel payment PWA  
**Architecture:** Next.js + TypeScript + Prisma + MySQL + PayPal Sandbox  
**Related documents:** PRD v1.2, `architecture.md`, `threat-model.md`, `designs.md`

> **Scope:** This API is for a hackathon prototype using PayPal Sandbox. It must not be represented as a production cross-border payment network. Sandbox payments do not move real money. Exchange-rate values are indicative unless an explicitly documented provider contract guarantees otherwise.

---

## 1. Contract conventions

### 1.1 Base path and format

- Base path: `/api`
- Transport: HTTPS in deployed environments; localhost HTTP is acceptable for local development.
- Request and response bodies: JSON, except where a future endpoint explicitly documents another content type.
- Character encoding: UTF-8.
- Dates/times: ISO 8601 UTC timestamps, e.g. `2026-10-31T12:00:00.000Z`.
- Monetary values: decimal strings, not JavaScript floating-point numbers. Example: `"12.34"`.
- Currency: three-letter uppercase ISO 4217 code where supported, e.g. `"USD"` or `"INR"`.
- IDs: opaque strings generated by the application. Clients must not infer meaning from them.
- Unknown fields: reject on security-sensitive mutation endpoints where practical; never silently use unknown fields as trusted values.
- Content type: clients should send `Content-Type: application/json` for JSON mutation requests.

All routes below are **proposed** and must be reconciled with the actual Next.js routing structure before implementation.

### 1.2 JSON success and error envelope

Success responses should return the endpoint-specific JSON shape described below. Do not wrap every success in a generic envelope unless the frontend and backend deliberately standardize on that convention.

Errors use this envelope:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Check the highlighted fields and try again.",
    "requestId": "req_opaque-id",
    "details": [
      {
        "field": "amount",
        "issue": "Amount must be a positive decimal value."
      }
    ]
  }
}
```

Rules:
- `code` is a stable machine-readable identifier.
- `message` is safe to display to users and must not include secrets, stack traces, SQL, internal paths, or raw provider error payloads.
- `requestId` helps correlate a report with redacted server logs.
- `details` is optional and contains safe, field-level validation information only.
- Do not return internal exception text to the client.

### 1.3 Common status codes

| HTTP status | Meaning |
|---|---|
| `200 OK` | Read succeeded or an existing operation returned its current result |
| `201 Created` | A new internal resource was created |
| `202 Accepted` | An asynchronous or not-yet-confirmed operation is being processed |
| `400 Bad Request` | Malformed JSON or invalid request shape |
| `401 Unauthorized` | A valid session or identity is missing |
| `403 Forbidden` | The caller is not permitted to access the resource |
| `404 Not Found` | Resource does not exist or is intentionally hidden from the caller |
| `409 Conflict` | State conflict, duplicate incompatible request, or idempotency conflict |
| `413 Content Too Large` | Request exceeds configured size limit |
| `415 Unsupported Media Type` | Unsupported content type |
| `422 Unprocessable Content` | Valid JSON but semantically invalid values |
| `429 Too Many Requests` | Rate limit exceeded |
| `502 Bad Gateway` | Provider returned an unusable response |
| `503 Service Unavailable` | Required service is temporarily unavailable |
| `504 Gateway Timeout` | Provider timed out and the operation's outcome may be uncertain |

Use `404` for both unknown and unauthorized resource identifiers when that helps prevent resource enumeration. Be consistent across routes.

### 1.4 Security and authority rules

1. The backend is authoritative for transaction state; PayPal is authoritative for provider-side order/capture status.
2. A client callback, redirect query parameter, browser state, local storage entry, or AI response must never mark a payment complete.
3. The client must not supply an authoritative amount, currency, merchant price, provider status, capture ID, or owner ID to the capture operation.
4. Payment creation and capture happen server-side using server-only credentials.
5. Every transaction read or mutation must enforce ownership or an explicitly documented demo-session policy.
6. Use server-side idempotency for payment creation and capture. Do not rely solely on a disabled button in the browser.
7. Never log secrets, access tokens, complete payment credentials, or unnecessary personal data.
8. Apply input validation, request size limits, rate limiting, and appropriate CSRF/origin protections for cookie-authenticated mutations.
9. AI tools are read-only and must use the same authorization rules as normal API routes.
10. Treat QR payloads, user messages, provider return parameters, and all client-supplied fields as untrusted.

## 2. Identity, session, and ownership prerequisite

**This must be decided before transaction endpoints are exposed.** The documents do not yet establish whether GlobalPay will use registered accounts or anonymous demo sessions.

Choose one approach and document it in the implementation:

### Option A — authenticated users
- Require a verified application session on every user-specific route.
- Derive the user ID from the server-validated session.
- Never accept `ownerId` or `userId` from the request body as authority.

### Option B — anonymous demo sessions
- Issue a high-entropy, opaque session identifier from a server-controlled mechanism.
- Prefer a `Secure`, `HttpOnly`, appropriately `SameSite` cookie for the session credential.
- Store only a hash or other safe representation of session tokens if server-side persistence is required.
- Rotate or expire sessions according to the selected policy.
- Apply CSRF/origin protection to cookie-authenticated mutations.
- Bind transactions and payment attempts to the server-resolved session.
- Do not use a guessable browser-generated ID as proof of ownership.

For both options:
- Merchant catalogue reads may be public if the catalogue contains no private data.
- Transaction list/detail, payment creation/capture, and personalized assistant context require authorization.
- Do not silently fall back to an unauthenticated global transaction list if identity/session validation fails.

Until this choice is made, user-specific routes below are **contract proposals with an unresolved authorization prerequisite**, not ready for public exposure.

## 3. Resource and state definitions

### 3.1 Transaction status

Use a controlled enum internally and in API responses. Recommended MVP values:

- `CREATED` — internal transaction created; payment provider order may not yet exist.
- `AWAITING_APPROVAL` — provider order created and awaiting user approval.
- `CAPTURE_PENDING` — capture has been requested or is being reconciled.
- `COMPLETED` — provider capture verified by the backend.
- `CANCELLED` — cancellation/abandonment is confirmed according to the implemented flow.
- `FAILED` — failure is confirmed and no successful capture exists for the attempt.
- `STATUS_UNKNOWN` — provider outcome cannot yet be confirmed.

Do not transition `STATUS_UNKNOWN` to `FAILED` merely because a request timed out. Reconcile with PayPal first. If the implementation needs a separate `EXPIRED` state, add it consistently to the database, API, and UI contracts.

### 3.2 Monetary data

Example:

```json
{
  "amount": "24.50",
  "currency": "USD"
}
```

- Decimal strings avoid precision loss from binary floating-point arithmetic.
- Validate allowed precision and range server-side for the selected currency.
- Keep the transaction's requested amount/currency distinct from any indicative converted amount.
- Do not assume a quote amount is the final PayPal settlement amount.
- If a value is unknown, use `null` or omit it according to the endpoint contract; do not substitute `0`.

### 3.3 Public transaction representation

The client-facing transaction object should contain only fields required by the UI:

```json
{
  "id": "txn_opaque-id",
  "merchant": {
    "id": "merch_opaque-id",
    "name": "Demo Merchant"
  },
  "amount": "24.50",
  "currency": "USD",
  "status": "AWAITING_APPROVAL",
  "quote": {
    "baseAmount": "2200.00",
    "baseCurrency": "INR",
    "convertedAmount": "24.50",
    "convertedCurrency": "USD",
    "rate": "0.011136",
    "source": "configured-rate-provider",
    "asOf": "2026-10-31T12:00:00.000Z",
    "indicative": true
  },
  "createdAt": "2026-10-31T12:00:00.000Z",
  "updatedAt": "2026-10-31T12:00:00.000Z"
}
```

The example is illustrative. Do not hard-code this merchant, quote, rate, or timestamp as real data. The implementation may omit `quote` if no quote is associated with a transaction. Provider order/capture identifiers should not be returned unless the UI has a concrete, safe need for them.

| Method | Route | Auth | Purpose |
|---|---|---|---|

| `POST` | `/api/assistant` | Required when context is personalized | Send a message to the read-only assistant |

An endpoint can be combined or renamed during implementation, but keep the resulting contract consistent across the frontend, tests, and documentation.

## 5. Merchant endpoints

### 5.1 `GET /api/merchants`

**Purpose:** Return supported demo merchants.

**Query parameters**
- `category` (optional): known category identifier.
- `demoQrOnly=true` (optional): restrict results to seeded active demo merchants with supported QR identifiers.
- `limit` (optional): integer, default `20`, configured maximum `50`.
- `cursor` (optional): opaque pagination cursor if cursor pagination is implemented.

**Success — `200 OK`**

```json
{
  "items": [
    {
      "id": "merch_opaque-id",
      "name": "Demo Merchant",
      "category": "food",
      "description": "Sample merchant for the GlobalPay demo.",
      "countryCode": "IN",
      "displayCurrency": "INR",
      "supportedMethods": ["PAYPAL_SANDBOX"],
      "isDemo": true
    }
  ],
  "nextCursor": null
}
```

Rules:
- Only return merchant fields approved for public display.
- Demo merchant summaries may include the seeded `demoQrIdentifier` used by the controlled demo QR selector.
- `supportedMethods` must reflect implemented server capability, not an aspirational roadmap.
- `isDemo` should be true for sample records.
- Do not fabricate ratings, reviews, verification badges, or acceptance coverage.

### 5.2 `GET /api/merchants/:id`

**Success — `200 OK`**

```json
{
  "item": {
    "id": "merch_opaque-id",
    "name": "Demo Merchant",
    "category": "food",
    "description": "Sample merchant for the GlobalPay demo.",
    "countryCode": "IN",
    "displayCurrency": "INR",
    "supportedMethods": ["PAYPAL_SANDBOX"],
    "isDemo": true
  }
}
```

- `404 NOT_FOUND` if no matching merchant exists.
- Only return a payment method if it is configured and supported.
- Merchant IDs are opaque; do not trust client-supplied merchant descriptions or currency as authoritative payment configuration.

### 5.3 `GET /api/merchants/demo-qr/:identifier`

Resolves a seeded, active demo merchant using its exact GlobalPay demo QR identifier.
The supported identifier format is `qr_demo_<country-code>_<merchant-key>_<two-digit-sequence>`
(for example, `qr_demo_jp_metro_01`). The server validates the format and resolves
the merchant from the catalogue; QR contents never supply authoritative merchant
names, prices, currencies, or payment methods. Unsupported identifiers return
`422 VALIDATION_ERROR`; unknown or inactive merchants return `404 NOT_FOUND`.
The endpoint does not create a transaction.

## 6. Currency quote endpoint

### `POST /api/currency/quote`

**Purpose:** Request an indicative conversion quote. This endpoint does not create a payment and does not guarantee a final settlement rate.

**Request**

```json
{
  "baseAmount": "2200.00",
  "baseCurrency": "INR",
  "quoteCurrency": "USD"
}
```

Validation:
- `baseAmount` must be a positive decimal string within configured limits.
- Currency codes must be uppercase and supported by the configured rate source.
- Reject unsupported currencies and malformed decimal values.
- Enforce a request body size limit and a rate limit.
- Do not accept a client-supplied exchange rate or source as authoritative.

**Success — `200 OK`**

```json
{
  "quote": {
    "baseAmount": "2200.00",
    "baseCurrency": "INR",
    "convertedAmount": "24.50",
    "convertedCurrency": "USD",
    "rate": "0.011136",
    "source": "configured-rate-provider",
    "asOf": "2026-10-31T12:00:00.000Z",
    "indicative": true,
    "expiresAt": "2026-10-31T12:05:00.000Z"
  },
  "disclaimer": "Indicative estimate only; the final conversion amount may differ."
}
```

The numbers are illustrative, not a statement about an actual exchange rate.

Rules:
- `source` must identify the configured source truthfully.
- `asOf` is when the rate data was observed or supplied by the source, not merely when the API response was generated.
- `expiresAt` is optional if no meaningful expiry policy is implemented.
- If no trustworthy rate is available, return a safe error; do not silently return a made-up, stale, or hard-coded “live” rate.
- Store a quote snapshot with a transaction only if the product requires it and the source/time are preserved.
- The server should use a decimal-safe calculation strategy.

Possible errors:
- `422 UNSUPPORTED_CURRENCY`
- `422 INVALID_AMOUNT`
- `429 RATE_LIMITED`
- `503 QUOTE_UNAVAILABLE`

## 7. Transaction endpoints

### 7.1 `POST /api/transactions`

**Purpose:** Create the internal transaction record before creating a PayPal order.

**Request**

```json
{
  "merchantId": "merch_opaque-id",
  "amount": "24.50",
  "currency": "USD",
  "quoteId": "quote_opaque-id"
}
```

`quoteId` is optional if the implementation does not persist quotes as resources. If quotes are stored, verify that the quote exists, is usable, and matches the requested currency/amount policy.

The request must **not** include `ownerId`, `userId`, a trusted merchant name, provider status, or a provider capture ID.

**Server behavior**
1. Authenticate/resolve the caller's session.
2. Validate the merchant against server-side data and ensure it supports the intended demo flow.
3. Resolve the merchant's configured demo amount on the server; reject a client amount that differs. Validate currency, precision, and applicable limits.
4. If a quote is referenced, validate it and store the relevant snapshot.
5. Create a transaction owned by the resolved user/session, initially `CREATED`.
6. Return only the public transaction representation.

**Success — `201 Created`**

```json
{
  "transaction": {
    "id": "txn_opaque-id",
    "merchant": {
      "id": "merch_opaque-id",
      "name": "Demo Merchant"
    },
    "amount": "24.50",
    "currency": "USD",
    "status": "CREATED",
    "createdAt": "2026-10-31T12:00:00.000Z",
    "updatedAt": "2026-10-31T12:00:00.000Z"
  }
}
```

Possible errors:
- `401 UNAUTHENTICATED`
- `404 MERCHANT_NOT_FOUND`
- `422 INVALID_AMOUNT`
- `422 UNSUPPORTED_CURRENCY`
- `422 QUOTE_INVALID_OR_EXPIRED`
- `429 RATE_LIMITED`

**Important:** This creates an internal record, not a completed payment and not necessarily a provider order.

### 7.2 `GET /api/transactions`

**Purpose:** List the authenticated user's or resolved demo session's transactions.

**Query parameters**
- `limit`: optional integer, default `20`, maximum `50`.
- `cursor`: optional opaque pagination cursor.
- `status`: optional valid transaction status filter.

**Success — `200 OK`**

```json
{
  "items": [
    {
      "id": "txn_opaque-id",
      "merchant": {
        "id": "merch_opaque-id",
        "name": "Demo Merchant"
      },
      "amount": "24.50",
      "currency": "USD",
      "status": "COMPLETED",
      "createdAt": "2026-10-31T12:00:00.000Z",
      "updatedAt": "2026-10-31T12:01:00.000Z"
    }
  ],
  "nextCursor": null
}
```

Rules:
- Scope the database query to the authenticated user/session before applying filters or pagination.
- Do not fetch all records and filter ownership in the browser.
- Do not return provider secrets or raw provider payloads.
- Return an empty list if the caller has no transactions.

### 7.3 `GET /api/transactions/:id`

**Purpose:** Return the current server-known state of a transaction.

**Success — `200 OK`**

```json
{
  "transaction": {
    "id": "txn_opaque-id",
    "merchant": {
      "name": "Demo Merchant",
      "countryCode": "JP"
    },
    "amount": "24.50",
    "currency": "USD",
    "status": "STATUS_UNKNOWN",
    "indicativeEstimate": {
      "homeCurrency": "EUR",
      "estimatedHomeAmount": "22.10",
      "rate": "0.902",
      "baseCurrency": "USD",
      "quoteCurrency": "EUR",
      "asOf": "2026-10-31T11:55:00.000Z"
    },
    "createdAt": "2026-10-31T12:00:00.000Z"
  }
}
```

Rules:
- The response contains only receipt-safe transaction and merchant fields. It may include `completedAt` only when the server stored a verified completion time, and `providerCaptureId` only for a completed PayPal Sandbox attempt with a verified capture timestamp and reference. Omit either field when unavailable.
- `indicativeEstimate` is optional and contains only the stored transaction estimate and quote snapshot fields. `asOf`, `baseCurrency`, and `quoteCurrency` may be omitted if absent from the snapshot; never substitute the transaction timestamp for a quote timestamp.
- The displayed transaction reference is the GlobalPay transaction `id`. A provider capture reference is not proof of settlement and must not imply that a real-world merchant received funds.
- Do not return session/token material, idempotency data, internal payment payloads, or unrelated database fields.
- The status is the server's current known state, not a claim that the provider is reachable at this instant.
- If the last provider result is ambiguous, preserve `STATUS_UNKNOWN` or the applicable pending state.
- Do not automatically capture a payment as a side effect of a normal read.
- `404 NOT_FOUND` for an unknown or inaccessible transaction.

## 8. PayPal Sandbox endpoints

These endpoints require special care. They must use server-only PayPal credentials and must be implemented against the actual PayPal Sandbox API/SDK version selected for the project. Provider-specific details must be checked against the official documentation during implementation.

### 8.1 `POST /api/payments/paypal/create`

**Purpose:** Create or retrieve the provider order associated with an existing internal transaction.

**Request**

```json
{
  "transactionId": "txn_opaque-id",
  "idempotencyKey": "client-generated-unique-operation-key"
}
```

Rules:
- `transactionId` must identify a transaction owned by the current user/session.
- `idempotencyKey` must be bounded in length and treated as untrusted input; scope it to the owner and operation.
- The server resolves the authoritative amount, currency, merchant configuration, and transaction status from stored data.
- Require current server-side payment eligibility (including simulated bank-link status) before creating a new PayPal order.
- Do not accept an amount, currency, recipient, provider status, or `ownerId` from the client as authoritative.
- Persist the provider order reference and operation result before returning success.
- Repeated identical requests should return the existing order/result where safe rather than creating a new order.
- Reuse of the same idempotency key with materially different input should return `409 IDEMPOTENCY_CONFLICT`.
- Prevent concurrent duplicate order creation with a database constraint/lock or another reliable server-side coordination mechanism.

**Success — `200 OK` for an idempotent replay, or `201 Created` for a newly created order**

```json
{
  "transactionId": "txn_opaque-id",
  "status": "AWAITING_APPROVAL",
  "checkoutUrl": "https://www.sandbox.paypal.com/...",
  "sandbox": true
}
```

The checkout URL is an example placeholder. Return only a URL obtained from the trusted provider response and validate it against the expected PayPal Sandbox host/allowlist before use. Never construct it from arbitrary client input.

Possible errors:
- `401 UNAUTHENTICATED`
- `404 TRANSACTION_NOT_FOUND`
- `409 TRANSACTION_STATE_CONFLICT`
- `409 IDEMPOTENCY_CONFLICT`
- `422 PAYMENT_METHOD_UNAVAILABLE`
- `429 RATE_LIMITED`
- `502 PAYPAL_PROVIDER_ERROR`
- `503 PAYPAL_UNAVAILABLE`
- `504 PAYPAL_TIMEOUT`

**Timeout rule:** if the provider may have created an order but the response was lost, record the operation as uncertain and reconcile before issuing a new provider order. Do not assume a timeout means no order exists.

### 8.2 `POST /api/payments/paypal/capture`

**Purpose:** Capture an approved Sandbox order for an existing transaction and verify the resulting provider state.

**Request**

```json
{
  "transactionId": "txn_opaque-id",
  "idempotencyKey": "client-generated-unique-operation-key"
}
```

The client must not supply a trusted PayPal order ID, capture ID, amount, currency, payee, or final status. The server retrieves the order reference associated with the owned transaction.

**Server behavior**
1. Resolve and authorize the transaction.
2. For a fresh capture, use an atomic conditional transition from `AWAITING_APPROVAL`; `CAPTURE_PENDING` is not eligible for fresh acquisition.
3. For `STATUS_UNKNOWN` or stale `CAPTURE_PENDING`, acquire a database-backed per-attempt lease before querying PayPal. Recovery must query the stored order before deciding whether capture is appropriate.
4. If inquiry confirms an existing completed capture, validate its capture ID, status, exact decimal amount, currency, and configured payee and recover it without another capture. Only an approved order with no capture may proceed to capture.
5. Reuse one stable PayPal request ID for the logical payment attempt, independent of HTTP retry/idempotency keys.
6. Verify order/capture identity, status, amount, currency, and the required configured payee. Missing evidence is not substituted with expected values.
7. If PayPal returned a capture but any verification fails or data is missing, persist transaction and attempt as `STATUS_UNKNOWN`, set `reconciliationNeeded: true`, retain a supplied capture ID, and write a structured event. Never mark the operation `FAILED`/`DENIED`.
8. Persist related transaction/attempt changes atomically where possible, with reconciliation for provider/database partial failure.
9. Return the current safe public transaction state; unresolved outcomes use `202 Accepted` and cannot initiate another capture without a successful provider inquiry.

**Success — `200 OK`**

```json
{
  "transaction": {
    "id": "txn_opaque-id",
    "amount": "24.50",
    "currency": "USD",
    "status": "COMPLETED",
    "updatedAt": "2026-10-31T12:01:00.000Z"
  },
  "payment": {
    "provider": "PAYPAL",
    "environment": "SANDBOX",
    "status": "COMPLETED",
    "sandbox": true
  },
  "notice": "Sandbox test payment only — no real money moved."
}
```

This response is valid only after server-side verification confirms successful capture. Example data is illustrative.

For an accepted but not-yet-confirmed operation, return `202 Accepted`:

```json
{
  "transaction": {
    "id": "txn_opaque-id",
    "status": "CAPTURE_PENDING"
  },
  "message": "The payment status is still being verified."
}
```

For an ambiguous outcome, return `202 Accepted` or a safe `504` response according to the implementation's error policy, while persisting enough information to reconcile. Do not report `FAILED` solely because the HTTP request timed out.

The implementation returns `202 Accepted` with status `STATUS_UNKNOWN` when capture verification is incomplete or uncertain. The client must not present this as success or offer a blind new payment/capture. A later recovery request first queries PayPal and re-verifies status, amount, currency, capture ID, and payee.

Possible errors:
- `401 UNAUTHENTICATED`
- `404 TRANSACTION_NOT_FOUND`
- `409 TRANSACTION_STATE_CONFLICT`
- `409 IDEMPOTENCY_CONFLICT`
- `422 ORDER_NOT_APPROVED`
- `422 PROVIDER_DATA_MISMATCH`
- `429 RATE_LIMITED`
- `502 PAYPAL_PROVIDER_ERROR`
- `503 PAYPAL_UNAVAILABLE`
- `504 PAYMENT_STATUS_UNCONFIRMED`

### 8.3 Provider return / browser callback

The provider may return the browser to a frontend route containing a provider token or other non-secret reference required by the selected integration. That return is **not proof of payment completion**.

- Treat all query parameters as untrusted.
- Do not mark a transaction complete in the browser.
- Call the server-side transaction/status endpoint to display current state.
- The server must verify the provider result through trusted provider APIs.
- Do not put application secrets or internal authorization tokens in the return URL.
- Keep any provider-required return parameters to the minimum needed by the chosen integration.

### 8.4 Reconciliation requirements

Implement a repeatable way to resolve ambiguous provider outcomes:
- Retrieve the stored provider order/capture state using server-side credentials.
- Check whether a capture already exists before retrying capture.
- Update transaction state only from validated provider data.
- Make the reconciliation operation idempotent.
- Preserve an audit trail of state transitions without logging secrets.
- If reconciliation is not implemented, show an honest “status not confirmed” state and provide a safe manual retry/check path; do not fake a final outcome.

### 8.5 `POST /api/payments/paypal/cancel`

Called by the `/pay/cancel` page when PayPal returns the buyer to the cancel URL. Requires a valid session and same-origin request.

Request: `{ "token": "<PayPal order ID from the cancel URL>" }`

The server finds the session-owned attempt for this order, takes the per-attempt lease, and queries PayPal before changing anything:

| PayPal order state | Result |
|---|---|
| `CREATED` / `SAVED` / `PAYER_ACTION_REQUIRED` | `CANCELLED` (`failureCode: BUYER_CANCELLED`) |
| `EXPIRED`, or 404 for an attempt older than 3 hours | `CANCELLED` (`failureCode: PAYPAL_ORDER_EXPIRED`) |
| `VOIDED` | `FAILED` (`failureCode: ORDER_VOIDED`) |
| `APPROVED` / `COMPLETED` / provider unreachable | unchanged |

Response `200`: `{ "transactionId", "merchantId", "status", "outcome": "CANCELLED" | "EXPIRED" | "FAILED" | "UNCHANGED" }`. Repeated calls are idempotent. Never captures.

Errors: `401 UNAUTHENTICATED`, `403 FORBIDDEN`, `404 NOT_FOUND` (unknown or other-session token), `422 VALIDATION_ERROR`.

Abandoned approvals (buyer closed the PayPal window) are reconciled by `GET /api/transactions`, which checks at most 5 of the session's `AWAITING_APPROVAL` attempts older than 3 hours, no more than once per 10 minutes each, using the same rules (without the buyer-cancel row).

`POST /api/payments/paypal/create` returns `422 UNSUPPORTED_CURRENCY` before calling PayPal when the transaction currency is not a PayPal-supported currency, and when PayPal itself answers `CURRENCY_NOT_SUPPORTED`. The amount and currency are never converted.

## 9. AI assistant endpoint

### `POST /api/assistant`

**Purpose:** Answer product questions and explain authorized merchant, quote, or transaction data. The assistant is informational and read-only.

**Request**

```json
{
  "message": "What does this transaction status mean?",
  "transactionId": "txn_opaque-id"
}
```

`transactionId` is optional. If provided, the backend must authorize access before retrieving context. Apply a message length limit, request size limit, and per-session rate limit.

**Success — `200 OK`**

```json
{
  "answer": "This transaction is awaiting approval. It is not yet confirmed as completed.",
  "sources": [
    {
      "type": "transaction",
      "id": "txn_opaque-id"
    }
  ],
  "disclaimer": "AI answers may be imperfect. Check the transaction status for the latest server-confirmed information."
}
```

`source` metadata must not reveal internal system prompts, private database fields, or information the caller is not authorized to view.

Rules:
- The backend, not the model, decides what data the user is allowed to access.
- Only expose read-only tools such as retrieving an authorized transaction, merchant details, or quote metadata.
- The assistant must not create, capture, cancel, or approve payments.
- The assistant must not set transaction state, invent exchange rates/fees, or treat user claims as provider confirmation.
- If status is unknown or stale, say so.
- Never include API keys, PayPal credentials, system prompts, database connection strings, or raw provider payloads in model context.
- Enforce output and token limits, timeout handling, and rate limits.
- Sanitize or redact sensitive information before sending context to the model.
- Return a safe error if the AI provider is unavailable.

Possible errors:
- `401 UNAUTHENTICATED`
- `403 FORBIDDEN`
- `404 TRANSACTION_NOT_FOUND`
- `413 CONTENT_TOO_LARGE`
- `422 MESSAGE_INVALID`
- `429 RATE_LIMITED`
- `502 AI_PROVIDER_ERROR`
- `503 AI_UNAVAILABLE`
- `504 AI_TIMEOUT`

## 11. Validation and operational controls

Exact limits must be configured and documented in code. Suggested starting limits for a hackathon MVP:

| Input / operation | Suggested initial limit |
|---|---|
| JSON request body | 32 KB maximum for ordinary routes; smaller for assistant messages if practical |
| Merchant list `limit` | Default 20, maximum 50 |
| Transaction list `limit` | Default 20, maximum 50 |
| Assistant message | 2,000 characters maximum |
| Amount | Positive decimal string; range and decimal precision defined by supported currencies |
| Idempotency key | 16–128 characters, unique per logical operation and scoped to owner |
| Quote requests | Per-session/IP rate limit; tune for the demo |
| Payment create/capture | Strict per-session limits plus idempotency and state checks |
| Assistant requests | Per-session/IP rate limit and provider timeout |

These are **proposed defaults**, not guarantees of production suitability. Choose exact limits based on the chosen libraries, provider behavior, and demo traffic.

Additional controls:
- Validate JSON shape and types on the server using a schema validator.
- Reject `NaN`, `Infinity`, negative amounts, excessive precision, and malformed currency codes.
- Use parameterized Prisma queries; never concatenate untrusted input into SQL.
- Configure CORS narrowly if cross-origin access is needed.
- For cookie-based sessions, implement appropriate CSRF/origin protections.
- Use secure cookies in production.
- Return `Cache-Control: no-store` for personalized transaction and payment responses.
- Set appropriate cache headers for public merchant catalogue responses.
- Avoid caching payment status in a CDN or browser cache.
- Use a request/correlation ID in logs and error responses.
- Redact authorization headers, cookies, provider credentials, and sensitive payload fields.
- Never include payment mutation endpoints as callable AI tools.

## 12. Idempotency and concurrency

For payment mutations, the server should persist an operation record or equivalent idempotency state.

Recommended behavior:
1. Scope an idempotency key to the resolved owner/session and operation type.
2. Store a request fingerprint of the normalized, validated input.
3. If the same key and same fingerprint are repeated, return the existing operation or its current status.
4. If the same key is reused with a different fingerprint, return `409 IDEMPOTENCY_CONFLICT`.
5. Protect transaction/order state changes against concurrent requests.
6. Do not assume a database transaction can atomically commit with an external PayPal API call; design for partial failure and reconciliation.
7. Preserve enough provider references and operation state to discover whether a timed-out operation succeeded.
8. Use database uniqueness constraints where applicable; in-memory locks alone are not sufficient for deployed multi-instance applications.

For capture specifically, a repeated request must not create a second capture. Use provider-supported idempotency mechanisms where available and confirm the existing capture state before attempting a retry.

## 13. Contract tests

Implement automated tests that verify both response shape and security invariants.

### Merchant and quote
- Valid merchant list returns only public fields.
- Unknown merchant returns `404`.
- Unsupported currency is rejected.
- Invalid, negative, zero, excessively precise, or malformed amounts are rejected.
- Missing quote source does not result in a fabricated live quote.

### Transaction ownership
- Missing session is rejected for user-specific routes.
- User/session A cannot list or retrieve user/session B's transactions.
- A caller cannot create a transaction for a client-supplied owner ID.
- Invalid merchant, quote, or currency cannot create a transaction.
- Pagination and filtering remain owner-scoped.

### PayPal create
- The server uses stored transaction amount/currency, not client overrides.
- Repeated same idempotency key returns the same logical operation.
- Conflicting reuse returns `409`.
- Concurrent requests do not create duplicate provider orders.
- Provider timeout is recorded as uncertain and reconciled safely.
- Client-provided checkout URLs are ignored.

### PayPal capture
- Capture is rejected for a transaction the caller does not own.
- Capture is rejected if no valid associated provider order exists.
- An unapproved order cannot be captured as completed.
- A mismatched amount/currency/order/payee cannot become `COMPLETED`.
- Client-supplied capture ID or `status: "COMPLETED"` is ignored/rejected.
- Repeated capture requests do not duplicate capture.
- A timeout does not automatically set the transaction to `FAILED`.
- `CAPTURE_PENDING` cannot be acquired as a fresh capture; concurrent different-key requests dispatch at most one capture.
- Concurrent recovery requests cannot claim the same attempt; completed captures are recovered without another capture.
- A response with a missing capture ID/status/amount/currency/payee remains uncertain, preserves any supplied capture ID, and requires reconciliation.
- A browser return/callback alone cannot mark the transaction complete.
- `COMPLETED` is returned only after trusted server-side verification.

### AI assistant
- Assistant cannot read an unauthorized transaction.
- Assistant tools are read-only.
- Prompt injection cannot enable payment mutation tools or expose secrets.
- The assistant reports unknown status honestly.
- Provider timeout and rate-limit behavior are safe.

## 14. Implementation notes and unresolved decisions

This document defines a proposed contract, not a claim that the routes or behavior exist. Resolve these before implementation:

1. **Session model:** authenticated accounts or server-issued anonymous demo sessions.
2. **Currency quote source:** select a provider or a clearly labelled fixed demo rate source; never describe a static value as a live rate.
3. **Merchant data:** decide which records are demo fixtures and how their supported payment methods are configured.
4. **PayPal integration version:** select the official SDK/API path and verify current order creation, approval, capture, idempotency, and response fields against official PayPal documentation.
5. **Quote persistence:** decide whether quotes have their own database model or are stored as immutable snapshots on transactions.
6. **Transaction status model:** keep API enum, Prisma enum, payment flow, and UI labels aligned.
7. **Reconciliation:** implement a safe provider-status check for ambiguous create/capture outcomes.
8. **Rate limits:** set actual values in the server implementation and tests.
9. **Error mapping:** implement a central mapping from internal/provider errors to the safe API error envelope.
10. **CSRF and origin policy:** decide based on the selected session mechanism and deployment topology.

### Implementation completion criteria

The API contract is ready to be considered implemented only when:
- Routes and schemas exist in the codebase.
- Every user-specific route enforces the chosen ownership model.
- The frontend uses the documented request/response shapes.
- Provider credentials remain server-only.
- Payment state changes are verified and idempotent.
- Error cases are tested.
- No client-side or AI-generated value can mark a payment complete.
- Sandbox disclosures are visible in payment initiation and completion flows.
